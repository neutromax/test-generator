# Enterprise Test Generator — Project Handoff

> A complete, self-contained description of the project: what it does, how it is
> built, how to run it, and its known limitations. Written so another AI (or a
> new developer) can pick it up with zero prior context.

---

## 1. One-line summary

A **local, privacy-preserving Streamlit app** that takes a GitHub repository and
generates test suites for it in two ways: (a) by producing a rich prompt you paste
into GitHub Copilot Chat, or (b) by automatically generating **and running** tests
using **local Ollama LLMs** — with no external/cloud APIs (company policy blocks
external APIs).

---

## 2. Why it exists / problem it solves

- Writing tests for an unfamiliar repo is slow and tedious.
- Company policy **blocks external AI APIs** (no OpenAI/Anthropic/etc.), so all AI
  must run **locally**.
- Goal: point the tool at a repo and get test scaffolding (and, where possible,
  runnable, passing tests) generated by local models under a supervisor model.

---

## 3. Two engines (important distinction)

The app has **two independent ways** to generate tests:

### Engine A — Manual "Enterprise Prompt" (for GitHub Copilot Chat)
- Builds a **static instruction template** (`Test_Prompt.md`) with only the repo
  URL and local path injected via a Python f-string. **No AI or code analysis
  happens here** — it's pure string templating.
- The template instructs an **agentic tool (Copilot Chat)** to run a 9-phase
  workflow: Repository Discovery → Code Understanding → Feature Identification →
  Spec Generation → **Human Approval Gate** → Test Script Generation → Coverage
  Analysis → Test Execution → Results Reporting.
- The app copies this prompt to the clipboard; **you paste it into Copilot Chat**,
  which does the actual reading of files and writing of tests.
- Built by `build_prompt()` in `src/generate_test_prompt.py`.

### Engine B — Automated Orchestrator (local Ollama models)
- Uses **local Ollama models** to generate tests directly, then extracts runnable
  `.py` files, installs the repo's dependencies, runs `pytest`, and reports
  pass/fail. Optionally self-corrects failing tests.
- This is the main focus of recent work.

| | Engine A (Enterprise prompt) | Engine B (Orchestrator) |
|---|---|---|
| Who generates tests | You + **Copilot Chat** | **Local Ollama models** |
| Reads real code? | Copilot does | Yes — code injected into prompt |
| Prompt | Static template + 2 variables | Dynamic, code-grounded |
| Output | Full `tests/` tree + reports | One runnable test file per task |
| Runs tests? | Copilot may | Yes (pytest) + self-correction |

## 4. Architecture (Engine B — the orchestrator)

```
Streamlit UI (app.py)
        │
        ├── OllamaClient ............ talks to Ollama server (localhost:11434)
        │
        └── Orchestrator (src/orchestrator/)
              ├── TaskRouter ......... builds a dependency-ordered task queue
              ├── ModelSelector ...... routes each task type to a model
              ├── MasterSupervisor ... validates output quality (GOLD/SILVER/BRONZE)
              └── CacheManager ....... SQLite cache of results (.cache/test_results.db)
```

### End-to-end pipeline (per run)
```
1. Clear stale artifacts (old test files) for the repo
2. Create tasks for selected test types → TaskRouter
3. Build execution queue (topological sort by dependencies)
4. For each task:
     a. ModelSelector picks a model
     b. gather_source_context() reads REAL repo source (grounding)
     c. build_symbol_index() extracts the real importable names
     d. create_task_prompt() builds a code-grounded prompt
     e. OllamaClient.generate() produces the test
     f. MasterSupervisor validates (GOLD/SILVER/BRONZE)
     g. Save .md + extract runnable .py into tests/test_scripts/
     h. Cache the result
5. UI: "Install Repo Dependencies" (pip install -e .) so imports resolve
6. UI: "Run Generated Tests" → pytest → parsed pass/fail breakdown
7. UI: "Auto-Fix Failing Tests" → self-correction loop (optional)
```

## 5. The models (Ollama)

| Model | Role | Notes |
|-------|------|-------|
| `llama3.1:8b` | Master / supervisor / security tasks | ~4.9 GB |
| `qwen2.5-coder:7b` | Worker — code/unit/integration | ~4.7 GB |
| `gemma3` (`gemma3:latest`) | Worker — E2E/API/balanced | ~3.3 GB |

- Ollama server: `http://localhost:11434`
- Model-name matching is **tolerant of the `:latest` tag** (so `gemma3` matches
  `gemma3:latest`).

### Model routing (ModelSelector)
- unit/integration/linting → prefer `qwen2.5-coder:7b`
- e2e/api → prefer `gemma3`
- security/vulnerability → prefer `llama3.1:8b`

## 6. Source-grounding (the key to accuracy)

Small local models hallucinate if they only get generic instructions. To fix this,
`create_task_prompt()` builds a **code-grounded** prompt containing three parts:

1. **PROJECT TESTING GOALS** — a short (~600 char) excerpt from the repo's
   `Test_Prompt.md` (high-level intent).
2. **IMPORTABLE SYMBOLS** — an explicit allow-list of the real importable names,
   parsed from the actual source by `build_symbol_index()`, e.g.
   `from inflection import camelize, pluralize, singularize, ...`.
   The model is told to import **only** these names.
3. **REPOSITORY SOURCE (ground truth)** — the actual code of a few small,
   function-rich modules, gathered by `gather_source_context()`.

Helpers:
- `discover_package_import_root(repo)` → finds the import root and top-level
  package (handles `src/<pkg>` layouts and top-level packages).
- `gather_source_context(repo, max_chars=3000)` → picks small, function-rich
  modules (INCLUDING `__init__.py`, since some packages put their whole API there)
  and returns bounded source text.
- `build_symbol_index(source)` → parses `# ===== Module: X =====` headers and the
  top-level `class`/`def` names to produce the import allow-list.

## 7. Execution bridge (generation → runnable tests)

- `extract_python_code(content)` — pulls Python from the model's markdown output.
  Robust to **unclosed code fences** (truncated output): it takes everything after
  the first ```` ``` ```` up to a closing fence if present.
- `save_orchestration_result()` — saves the full `.md` AND writes a runnable
  `tests/test_scripts/<task>_test.py`.
- A generated `conftest.py` adds the repo's import root to `sys.path` so the
  package is importable.
- `install_repo_dependencies(repo)` — runs `pip install -e .` (or from
  `requirements*.txt`) so the repo's own deps (e.g. `werkzeug` for Flask) exist.
- `run_tests_and_coverage(repo)` — runs pytest with `--confcutdir` / `--rootdir`
  set to `test_scripts/` so the **target repo's own `tests/conftest.py` is NOT
  loaded** (that used to abort collection).
- `parse_pytest_output(output)` — turns raw pytest output into a readable
  per-test list of `{name, status, reason}` for the UI (✅/❌/🟠 with reasons).

---

## 8. Self-correction loop (quality mode)

When some generated tests fail, the UI shows **"🔧 Auto-Fix Failing Tests"**.
For each failing test file:
1. `run_pytest_single()` runs pytest on just that file.
2. `build_fix_prompt()` sends the failing test code + the pytest failure output +
   the real source + symbol allow-list back to the model.
3. The model returns a corrected test; it is re-run.
4. The fix is **kept only if the pass count does not decrease** (otherwise
   reverted). Capped at **2 rounds per file**.

---

## 9. Quality validation (MasterSupervisor)

- **GOLD** (approve) / **SILVER** (minor issues → correction prompt) /
  **BRONZE** (redo).
- Checks: non-empty, has test structure (`def test_`), minimum length, and (inside
  fenced code blocks only) balanced parentheses/brackets and common typos.
- Deliberately **not** overly strict: it does NOT fail on `...`/`etc.` or on test
  functions lacking `return` (earlier false-positive sources).

---

## 10. Caching (CacheManager)

- SQLite DB at `.cache/test_results.db`.
- Keys results by repo hash + test type; detects input changes via file hashes;
  7-day retention; statuses: PENDING/IN_PROGRESS/DONE/FAILED/INVALID/SKIPPED.
- Re-running the same repo/type returns the cached result instantly.
- If a cached result file is missing on disk, the entry is marked INVALID and
  regenerated.

## 13. How to run

```powershell
# 1. Ensure Ollama is running and models are present
ollama serve                      # (or the Ollama desktop app)
ollama list                       # should show llama3.1:8b, qwen2.5-coder:7b, gemma3

# 2. Start the app
cd "d:\test generator"
streamlit run app.py              # opens http://localhost:8501
```

### Using Engine B (orchestrator) in the UI
1. Enter a GitHub URL → **Generate Test Prompt** → **Proceed**.
2. Select test types (start with **Unit Tests**) → **Run Test Orchestration**.
3. **📦 Install Repo Dependencies** (one time per repo).
4. **▶️ Run Generated Tests** → see per-test pass/fail.
5. If failures → **🔧 Auto-Fix Failing Tests** (optional, slower).

## 14. Key configuration / tuning knobs

In `src/ollama_client.py` (`generate()` options) and `app.py`:

| Knob | Location | Current | Effect |
|------|----------|---------|--------|
| `num_predict` | ollama_client | 512 | Max output tokens (↑ = longer tests, slower) |
| `num_ctx` | ollama_client | 4096 | Context window (↑ = more code seen, slower) |
| `temperature` | ollama_client | 0.3 | Lower = more deterministic |
| `keep_alive` | ollama_client | "15m" | Keeps model resident (avoids reload) |
| `timeout` | ollama_client | 1200s | Per-generation timeout |
| `max_chars` | `gather_source_context` | 3000 | How much source is injected |
| tests requested | `create_task_prompt` | "exactly 3" | Fewer = completes within token cap |

## 15. KNOWN DRAWBACKS & LIMITATIONS (read carefully)

### 15.1 Hardware / speed (the biggest issue)
- The target machine has **no NVIDIA GPU** (only Intel Iris Xe integrated
  graphics, which Ollama cannot accelerate). All inference is **CPU-only**.
- Measured throughput: **~1.3 tokens/second**. A single test generation takes
  **~4–13 minutes**. This is a hard physical limit, not a bug.
- Parallel "batches" do **not** actually parallelize on CPU (CPU-bound), so tasks
  run effectively sequentially.

### 15.2 Model quality (small local models)
- 7B/8B models **guess semantics**. Common failure patterns observed:
  - Instantiating objects with `None` where a real object is required
    (e.g. Flask tag classes need a `TaggedJSONSerializer`, not `None`).
  - Wrong expected values in assertions.
  - Occasionally confusing similarly named libraries (mitigated by the symbol
    allow-list, but not eliminated).
- Realistic pass rate on first draft: **partial** (e.g. Flask unit run = 5/10).
  Simple pure-function repos (e.g. `inflection`) do better.

### 15.3 No external APIs
- Company policy blocks cloud APIs, so you **cannot** offload to a fast, accurate
  hosted model. This caps both speed and quality.

### 15.4 The fundamental trade-off
- Speed vs. accuracy cannot both be maximized here:
  - Smaller model (e.g. `qwen2.5-coder:1.5b`) → ~4–5× faster but rougher tests.
  - Self-correction loop / bigger model → more accurate but 2–3× slower.

### 15.5 Context-window limits
- Only a few small source modules fit in the prompt (max ~3000 chars of source at
  `num_ctx=4096`). Large modules are skipped or truncated, so tests may not cover
  big files well.

### 15.6 Output truncation
- With a low `num_predict`, long outputs can be cut off mid-file. Mitigations:
  ask for "exactly 3 short tests" and robust fence extraction — but truncation can
  still occasionally produce an incomplete last test.

### 15.7 Test types beyond unit are weaker
- E2E / Security / API tests usually need app fixtures, clients, auth context, etc.
  Small models struggle to set these up, so those types have **lower pass rates**
  than unit tests.

### 15.8 Dependency installation required
- Generated tests import the real package, so the repo's deps must be installed
  (`pip install -e .`). This needs network/PyPI access and can be slow or fail for
  repos with heavy dependency trees.

### 15.9 Streamlit reactivity quirks
- Browser automation of the UI is flaky because Streamlit reruns the script
  frequently; scripted clicks can race with reruns. Manual clicking is reliable.

### 15.10 Engine A does no analysis
- The "Enterprise prompt" is a **static template**; all intelligence is deferred to
  whatever agent (Copilot) you paste it into. The app itself does not read code in
  Engine A.

## 16. Suggested next improvements (for whoever continues)

1. **GPU or hosted model** — the single biggest win for both speed and quality
   (blocked here by hardware + policy).
2. **Smaller fast model option** — pull `qwen2.5-coder:1.5b` and route to it for a
   "fast mode" toggle.
3. **Narrow-scope generation** — generate tests for ONE function at a time with its
   full source for higher per-test accuracy.
4. **Deeper self-correction** — more rounds, or run-time value probing.
5. **Trim the generic "PROJECT TESTING GOALS" block** — it can distract small
   models; removing it may sharpen output.
6. **Better module selection** — prioritize public API modules and split large
   files into function-level chunks.
